# 启动卡顿排查与优化指南

> 适用于本项目（PyQt6 桌面应用）  
> 日期: 2026-03-26

---

## 一、现象描述

程序启动后前几秒内：
- 点击侧边栏按钮无反应或延迟响应
- 窗口拖动/缩放卡顿
- 界面元素（图标、缩略图）空白等待
- 过几秒后恢复正常

**根因**：主线程在启动后的短暂窗口期内被大量同步初始化阻塞，事件循环无法及时处理用户输入。

### 3.3 方法三：QElapsedTimer（Qt 事件循环内精确计时）

```python
from PyQt6.QtCore import QElapsedTimer

class StartupProfiler:
    def __init__(self):
        self._timer = QElapsedTimer()
        self._timer.start()
        self._marks = []
    
    def mark(self, label: str):
        elapsed = self._timer.elapsed()
        self._marks.append((elapsed, label))
        print(f"[PERF] +{elapsed}ms  {label}")
    
    def report(self):
        print("\n===== 启动性能报告 =====")
        prev = 0
        for ms, label in self._marks:
            delta = ms - prev
            bar = "█" * max(1, delta // 20)
            print(f"  {ms:6d}ms (+{delta:4d}ms) {bar} {label}")
            prev = ms

# 用法: 在 main.py 全局创建
_sp = StartupProfiler()
# 在各处调用
_sp.mark("QApplication created")
_sp.mark("MainWindow.__init__ start")
_sp.mark("MainWindow.__init__ done")
# ...
# 最后
QTimer.singleShot(5000, _sp.report)
```

### 3.5 方法五：分析本项目的 `import_times.txt`

从这份日志里，可以直接看出哪些模块在启动阶段比较重。

#### 3.5.1 从 `cumulative` 看出的真实重模块

从这份日志里，以下 import 明显偏重：

| 模块 | 观测值 | 结论 |
|------|--------|------|
| `torch.functional` | `1100773us` | 非常重，说明启动阶段进入了深层 `torch` 导入链 |
| `torch.utils._debug_mode` | `1041946us` | 非常异常，不应在普通 UI 启动期这么早出现 |
| `torch.nn.attention` | `636379us` | 说明不只是基础 `torch`，连较深层功能也被带入 |
| `_sqlite3` | `298635us` | SQLite 冷启动成本不小，若再叠加 `integrity_check` 体感更差 |
| `cv2` | `243083us` | OpenCV 首次加载偏重，启动主路径应尽量避免 |
| `numpy` | `216541us` | 属于典型大模块，若与 `cv2` 一起进入主路径会放大卡顿 |
| `qtawesome` | `157816us` | 比预期更重，说明图标系统本身也有启动成本 |

#### 3.5.2 最可疑的启动导入链

结合 `import_times.txt` 与代码结构，最值得怀疑的是这条链：

```text
settings / gpu_utils / image_library_page / import_page
  -> core.check_cli
  -> core.detectors.bird_focus_detector
  -> torch / rawpy / exifread
```

关键证据包括：

```text
import time:      1335 |     244417 | utils.system.gpu_utils
import time:      1561 |     308382 | utils.sql.data_base
import time:      5545 |     430027 | ui.image_library_page
import time:      5449 |       7618 | ui.import_page
import time:    -12563 |      85234 | core.check_cli
import time:      1970 |       2768 | core.detectors.bird_focus_detector
```

这说明：
- `ui.image_library_page` 的累计 import 已达 **430ms**
- `gpu_utils`、`data_base` 都在早期主路径中
- `core.check_cli` 和 `bird_focus_detector` 在启动链中被提早拉入
- 进而把 `torch`、`rawpy`、`exifread` 一串重依赖带了进来

#### 3.5.3 针对本日志的明确判断

基于当前 `import_times.txt`，可以下结论：

1. **`torch` 导入链过重，而且进入启动期过早**
2. **`core.check_cli` / `bird_focus_detector` 被错误地放到了冷启动路径上**
3. **`sqlite3` + `BirdLibraryDB` 组合是启动卡顿的重要组成部分**
4. **`cv2` / `numpy` 不应在主界面刚可见时同步进入**
5. **`qtawesome` 图标初始化也值得一起优化，但优先级低于 `torch/cv2/db`**

### 3.6 方法六：事件循环阻塞检测

检测主线程事件循环被阻塞超过阈值的情况：

```python
from PyQt6.QtCore import QTimer, QElapsedTimer

class EventLoopMonitor:
    """检测主线程阻塞: 如果 QTimer 回调被延迟超过阈值, 说明主线程被占用"""
    
    def __init__(self, threshold_ms: int = 100):
        self._threshold = threshold_ms
        self._timer = QTimer()
        self._timer.setInterval(50)  # 期望每 50ms 触发
        self._timer.timeout.connect(self._check)
        self._elapsed = QElapsedTimer()
        self._elapsed.start()
        self._last_ms = self._elapsed.elapsed()
        self._timer.start()
    
    def _check(self):
        now = self._elapsed.elapsed()
        delta = now - self._last_ms
        if delta > self._threshold:
            print(f"[WARN] 主线程阻塞 {delta}ms (期望 50ms)")
        self._last_ms = now

# 在 QApplication 创建后立即启用:
_monitor = EventLoopMonitor(threshold_ms=100)
```

## 四、优化方案

### 4.1 已做的优化（当前代码中的）

| 优化 | 实现方式 |
|------|---------|
| 页面懒加载 | `_ensure_page_loaded` + 占位 Widget，页面构造推迟到首次切换 |
| 数据图表延迟 | `_charts_page_loaded` 标志 + 首次切换才 import |
| CUDA 探测后台化 | `threading.Thread` 异步执行 |
| 图库缓存后台加载 | `load_persistent_cache` 在后台线程 |
| 主体检测 warmup 后台 | `_SubjectDetectService` 队列线程 |
| 加载框遮盖 | 用户看到"正在加载"而非假死窗口 |
| `QTimer.singleShot` 错时 | 150/250/600/1200ms 分散初始化 |

### 4.2 可以进一步做的优化

#### 优先级 P0：效果最显著

**4.2.1 将 `BirdLibraryDB._init_db()` 移到后台线程**

当前 `_init_db` 在 `ImageLibraryPage.__init__` 中**主线程同步执行**，包含 `PRAGMA integrity_check`（大库耗时可达数百毫秒）。

```python
# 方案: DB 初始化在后台线程完成, 页面先用"加载中"状态
class BirdLibraryDB:
    def __init__(self, ...):
        self._ready = threading.Event()
        self._init_thread = threading.Thread(target=self._init_db_background, daemon=True)
        self._init_thread.start()
    
    def _init_db_background(self):
        self._init_db()  # 原逻辑
        self._ready.set()
    
    def query(self, sql, params):
        self._ready.wait()  # 确保初始化完成
        # ...原逻辑
```

**预计收益**：减少 200-400ms 主线程阻塞。

**4.2.2 `populate_tree` 异步化**

当前 `folder_panel.populate_tree()` 在主线程遍历文件夹树。改为后台 `QThread` 遍历，完成后通过信号更新 UI：

```python
class FolderTreeLoader(QThread):
    treeReady = pyqtSignal(list)  # 树节点数据
    
    def run(self):
        nodes = self._scan_folder_tree(root_path)
        self.treeReady.emit(nodes)

# 连接信号后在主线程一次性填充 QTreeWidget
```

**预计收益**：减少 100-300ms 主线程阻塞。

**4.2.3 `PRAGMA integrity_check` 降频或去除**

每次启动都做 `PRAGMA integrity_check` 非常昂贵。改为：
- 仅在上次非正常退出时执行（通过标志文件检测）
- 或改为 `PRAGMA quick_check`（只检查 B-tree 结构，不扫描行数据）
- 或完全移除，仅在用户手动触发"修复数据库"时执行

```python
def _init_db(self):
    # 检查上次是否正常退出
    sentinel = self.db_path.with_suffix('.running')
    if sentinel.exists():
        # 上次非正常退出，执行完整检查
        self._check_database_integrity()
    # 标记"运行中"
    sentinel.touch()
    # ...正常初始化
    # 在 close/atexit 时删除 sentinel
```

**预计收益**：减少 100-300ms（取决于数据库大小）。

#### 优先级 P1：有一定效果

**4.2.4 `cv2` import 延迟化**

`cv2` 在 `cache_manager.py`、`gpu_utils.py` 等模块顶层被 import，而这些模块在构造 `ImageLibraryPage` 时会被拉入。改为函数内 import：

```python
# 修改前 (cache_manager.py 顶部):
import cv2

# 修改后:
_cv2 = None
def _get_cv2():
    global _cv2
    if _cv2 is None:
        import cv2
        _cv2 = cv2
    return _cv2
```

> 注意：`watermark_dialog.py` 和 `bird_focus_detector.py` 中已经用了这个模式（`_get_cv2()`），可以推广到其他文件。

**预计收益**：减少 50-200ms。

**4.2.4-b 避免在启动期导入 `core.check_cli` / `bird_focus_detector`**

根据 `import_times.txt`，这两个模块在冷启动阶段已经进入 import 链，这是非常可疑的。应继续追踪：
- 谁在启动期 import 了 `core.check_cli`
- 是否只是为了拿某个常量/工具函数，结果把整条 `torch` 依赖链带进来
- 是否可以拆分为轻量模块，例如：

```text
core.check_cli
  -> core.check_cli_runtime      # 真正用 torch 的运行逻辑
  -> core.check_cli_types        # 轻量数据结构/常量
  -> core.check_cli_service      # 懒加载服务入口
```

**目标**：让 `main.py`、`main_window.py`、`image_library_page.py`、`import_page.py` 在冷启动阶段完全不 import `core.check_cli`。

**预计收益**：减少 300-1000ms（取决于是否连带切断 `torch` 导入链）。

**4.2.5 `ImageLibraryPage.init_ui()` 分阶段构造**

当前 `init_ui()` 一次性构造所有面板（文件夹面板、预览面板、信息面板、工具栏等）。改为：
- 先构造骨架（工具栏 + 空网格区）—— 用户可见可交互
- 侧面板等在 `QTimer.singleShot(0, ...)` 中分批构造

```python
def init_ui(self):
    self._build_skeleton()  # 工具栏 + 网格区, <50ms
    QTimer.singleShot(0, self._build_folder_panel)
    QTimer.singleShot(0, self._build_preview_panel)
    QTimer.singleShot(0, self._build_info_panel)
```

**预计收益**：将 200-400ms 的单次阻塞打散为多个 <50ms 的小段。

**4.2.6 `qta.icon()` 批量预缓存**

侧边栏 8 个按钮各调一次 `qta.icon(...)`，每次 QtAwesome 需要查找字体 + 渲染。改为一次创建所有图标：

```python
icons_needed = [
    ("fa6.images", button_color),
    ("mdi6.file-import-outline", button_color),
    # ...
]
# 批量创建，减少重复的字体查找开销
icon_cache = {name: qta.icon(name, color=color) for name, color in icons_needed}
```

**预计收益**：减少 20-50ms。

#### 优先级 P2：长期改善

**4.2.7 用 `QSplashScreen` 替换自定义加载框**

当前加载框是 `QDialog`，需要 `processEvents()` 手动驱动。`QSplashScreen` 可以在事件循环外自动绘制（但功能有限）。

**4.2.8 DLL 路径扫描优化**

`_configure_windows_dll_search_paths` 中 `os.walk(nvidia_root)` 改为只扫一层或缓存结果：

```python
# 修改前: os.walk 递归全树
# 修改后: 只加已知目录
known_nvidia_dirs = [nvidia_root]  # 或预存列表
for d in known_nvidia_dirs:
    if os.path.isdir(d):
        os.add_dll_directory(d)
```

**4.2.9 页面构造进一步推迟**

当前 `_ensure_page_loaded(0)` 和 `_ensure_page_loaded(1)` 在 `show_main_interface` 中以 150ms/250ms 就触发了。如果用户启动后默认在图库页，可以：
- 图库页 150ms 保持不变（用户要看）
- **导入页推迟到首次切换时才构造**（同数据图表页的策略）

```python
# 修改 show_main_interface:
QTimer.singleShot(150, lambda: self._ensure_page_loaded(0))  # 图库页, 必须
# 删除: QTimer.singleShot(250, lambda: self._ensure_page_loaded(1))
# 改为在 on_page_changed 中按需加载
```

**预计收益**：减少 100-200ms（导入页的构造不再在启动时执行）。

### 5.2 预期目标

| 指标 | 当前估计 | 优化后目标 |
|------|---------|-----------|
| 进程启动 → 加载框显示 | ~300ms | ~200ms |
